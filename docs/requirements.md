## 1. Purpose and scope

- REQ-1 [user] Build a structured decision register for grill-me: structured data captured during an interview gives a plan, documentation and a decision record for free.
- REQ-2 [user] Enforcement moves out of grill-me prose into the tool. A much more complex grill-me than the original is acceptable.
- REQ-3 [user] Causal and statistical purity are waived. There is no budget ceiling; the assistant asks before spending more than about USD 1.
- REQ-4 [user] The register is built from scratch. `reference/armG/` is a behavioural specification and a source of test ideas only; no code is copied from it or from the stock sequential-thinking server.
- REQ-5 [user] Only the grill-me chain uses the register (grill-me, wayfinder, write-a-prd via grill-me). Other skills stay on the stock sequential-thinking tool.
- REQ-6 Out of scope: the paid effectiveness evaluation, the evaluation harness and the harness cost-counter fix (owned by the research session in the research repository); changes to `~/.claude`, skills, hooks and `settings.json` (filed in the dotfiles repository under the user's rule); ADR draft generation by the register [user, deferred]; Windows and macOS binaries [user, "for now"].

## 2. Architecture

- REQ-10 [user] The register state is held in the server process's memory. A server process serves one Claude Code session at a time [verified: spike 1, two concurrent sessions had separate processes and counters]; after `/clear` the same process sees a new `session_id` [verified: spike 1, one trial], so the process sees a sequence of session ids, and REQ-26 binds an interview to one.
- REQ-11 [verified: spike 1] Hooks reach the live server with handler type `mcp_tool` (server reference `plugin:<plugin>:<server>`). A Stop-event `mcp_tool` hook reached the same process as the model's tool calls, and returning `{"decision":"block","reason":...}` as the tool's text blocked the Stop. A UserPromptSubmit `mcp_tool` hook also reached the same process. No socket, HTTP port or state file is used between hooks and server [design consequence of the above; spike 1 shows same-process handling but did not test for the absence of other channels].
- REQ-12 The product is a Claude Code plugin containing: the hook configuration, `.mcp.json`, and nothing compiled; implementation binaries are separate release assets (section 8). The plugin sits in a subdirectory of this repository (for example `plugin/`), with the marketplace manifest at the repository root, so that sessions opened at the repository root do not load the plugin's `.mcp.json` as a project server (REQ-82). [assistant]
- REQ-15 [open: the user's decision] Where the canonical grill-me skill text lives: shipped in the plugin (the dotfiles copy is then retired, filed in the dotfiles repository), or kept in the dotfiles repository and edited there. Until decided, the start list (REQ-24) holds exactly one full skill name, matched exactly as received, so that a second `grill-me` copy cannot start an interview whose skill text never logs items.
- REQ-13 [user] The server does nothing and enforces nothing unless an interview is active. Hooks are no-ops in every session without an active interview, so installing the plugin does not change the behaviour of unrelated sessions while the server is healthy. [verified: spike 1, plugin-level hooks fire in every session] When the binary is missing or the server is not connected, the hooks run in every session too; REQ-53 and REQ-77 cover that case.
- REQ-14 [user] Enforcement lives in the server and the hooks that call it; the skill text describes the interview but does not carry the enforcement. [from the interview: the enforcement surface is server plus hooks]

## 3. Interview lifecycle

- REQ-20 [user] An interview is started by hooks, not by the model: a UserPromptExpansion hook for a typed `/grill-me`, and a PreToolUse hook matching the Skill tool for a model-invoked skill; each passes the skill name and `${session_id}` to the server, which starts an interview only if the name exactly matches an entry on a configured list (REQ-15, REQ-24). [verified: spike 4, one trial per route on Claude Code 2.1.325; the Skill tool's input field was observed as `skill`, not documented]
- REQ-21 [user] First fallback: a `begin_interview` tool that the skill calls as its first step. Second fallback: if a model-facing mutating call (`log_item`, `resolve`, `park`, `reopen`) arrives while no interview is active and no unfinished journal exists (REQ-52), the server starts one and flags it as implicitly started; the flag appears in the decision log. [assistant: the restriction to model-facing mutating calls, and the journal exclusion] Hook-facing tools, `status`, `resume` and `end_interview` never start an interview, so plugin-level hooks in unrelated sessions cannot start one (REQ-13).
- REQ-22 [user] Starting an interview resets all counters and caps and stamps an interview id. Server state survives `/clear` and `/compact` [verified: spike 1, one trial each, `claude -p` stream-json only; interactive sessions untested, see section 12]. [assistant: the rest of this requirement] A start while an interview is active in the same session is a no-op that returns the existing interview id (a second `/grill-me`, a wayfinder or write-a-prd call, or a re-invocation after `/compact` must not wipe the register); a new interview needs the earlier one ended (REQ-23) or its session gone (REQ-26). When a new interview starts, the server archives only its own earlier journal, never another interview's, by moving it to an archive folder in the data directory.
- REQ-23 [user] The decision log is written by the server at every allowed finish attempt (REQ-43), including one allowed because the caps were spent (REQ-42), and at the end of an interview; writing it never depends on the model calling a tool. [assistant: the following mechanics] An allowed finish attempt with nothing open marks the interview complete but leaves it active and the journal in place, so grill-me's replay step can read the log and a later `reopen` or `log_item` clears the complete mark instead of triggering an implicit start. The interview ends, with the journal archived, on `end_interview`, on a session boundary (REQ-26), or when the server exits. `end_interview` called while items are open is refused unless it carries `abandon: true` and a reason; the log then records "ended incomplete by the model" and REQ-50's end notice says so. The log's file name includes the interview id, so a later interview never overwrites it.
- REQ-24 [assistant] The configured skill-name list starts with the single full name chosen under REQ-15; whether `wayfinder` and `write-a-prd` are listed is decided when the grill-me integration is built, because those skills call grill-me.
- REQ-26 [assistant] An interview is bound to the `session_id` it started in. A hook call carrying a different `session_id` (the user typed `/clear`, or resumed elsewhere) ends it as abandoned: the log is written and flagged incomplete, the journal is archived, and the gate does nothing for the new session. This check runs before REQ-22's no-op rule, so a `/grill-me` typed after `/clear` ends the old interview and starts a new one. Whether a compaction changes the `session_id` is unverified (section 12). A `SessionEnd` hook calling `end_interview` is a candidate if it is verified to be callable.

## 4. Data model

- REQ-30 [user] The register is a tree of items. Each item has: id, kind (`question`, `subquestion` or `decision`), text, optional parent, optional `depends_on` ids, status, and event history.
- REQ-31 [user] Status is one of Open, Resolved, Parked, Stale. A Resolved item always carries an answer, an answer source (`user` or `model`) and a one-line rationale; the implementation makes a Resolved item without these unrepresentable where the language allows, and rejects it at the interface where it does not. [assistant: answer and rationale must be non-empty after trimming and the rationale a single line; replay applies the same check and fails resume naming the line, as for REQ-60]
- REQ-32 [user] An answer source of `user` is accepted only if a user prompt arrived since the item's last model action, as counted by the prompt hook. Otherwise the call is rejected. [assistant: `log_item` may carry `answer`, `source` and `rationale` to record a decision the user volunteered in one call; with source `user` it is accepted only if a user prompt arrived since the previous Stop-hook call. Known limit: the check shows that a user prompt exists, not that it answered this item, and the model can still resolve several items as `user` after one prompt; whether to add a per-prompt budget is decided in ADR 0002.]
- REQ-33 [user] A Parked item records who parked it (`parked_by`: `user` or `model`) and a reason. A park by the model keeps the item blocking; a park the user asked for does not. [assistant: `parked_by` `user` is subject to the same user-prompt rule as REQ-32, so the model cannot clear the gate by claiming a user park.]
- REQ-38 [assistant] Transitions: `resolve` accepts Open, Stale and Parked items (a model-parked item can be resolved, or re-parked with `parked_by` `user` under REQ-33); `park` accepts Open, Stale and model-Parked items; `reopen` accepts Resolved items only; every other transition is an error naming the item id and its current status.
- REQ-34 A `decision` item can be resolved only with source `user`, and parked only with `parked_by` user. [assistant: derived from the change-request spike's specification C2; user to confirm in the stress-test]
- REQ-35 A branch is a parent item with at least N sub-questions; N = 2 and is a declared constant, not measured. [assistant] Enforcement points: `log_item` never rejects on branch size; the finish gate flags a parent that has children but fewer than N; `resolve` of a parent with fewer than N children is rejected. A `subquestion` requires a parent; a `question` or `decision` may have one; any kind may be a parent. [assistant]
- REQ-36 Reopening a Resolved item makes it Open and makes every Resolved item that depends on it, directly or transitively, Stale. A Stale item blocks finishing like an Open item and can be resolved again. [assistant: derived from C1]
- REQ-37 Optional fields beyond those above (options considered, recommendation, tags) are not in the first build. ADR drafting is deferred. [user]

## 5. Tools and hooks

- REQ-40 Tools: `begin_interview`, `log_item`, `resolve`, `park`, `reopen`, `status`, `resume`, `discard`, `end_interview`, plus the hook-facing tools `note_prompt`, `skill_started` and `check_stop`. Names, schemas and results are identical in every implementation. [assistant: proposal, to be finalised in the build plan] The three hook-facing tools reject any call that carries the model-call marker `_meta` `claudecode/toolUseId`, so the model cannot call `note_prompt` to forge a user prompt or call `check_stop` to spend the caps [verified: spikes 1 and 4 observed that hook-originated calls carry no `_meta` and model calls do, one trial each; a conformance scenario sends both forms]. [assistant]
- REQ-41 Four hook behaviours: the prompt counter (UserPromptSubmit calls `note_prompt`); the finish gate (Stop calls `check_stop` with `last_assistant_message`); and two start hooks (REQ-20). Hooks carry only the fixed input given in their configuration plus substituted fields (for example `${prompt}`, `${session_id}`) [verified: spike 4 for `${prompt}`, `${session_id}` and `${tool_input.skill}`; spike 1 and spike 4: hook-originated calls carry no `_meta`]. Substitution of `${last_assistant_message}` into the Stop hook's `mcp_tool` input, which REQ-43 depends on, delivered a 6,869-character message with quotes, backslashes, newlines, a question mark, unicode and a JSON fragment byte-identical (length and sha256 matched) [verified: spike 5, one trial, haiku, Claude Code 2.1.325; short and empty messages not tested; `docs/evidence/spike5/`].
- REQ-42 [user] The finish gate keeps ADR 0001's behaviour as starting values, counted per interview: at most 2 blocks per user prompt, 8 blocks to finish, 12 for unlogged questions; fail open. Claude Code itself limits consecutive Stop blocks to 8, reset by any tool call [recalled: from Claude Code documentation, not re-checked in a repo artefact; verify in the build]; the register's caps sit under that.
- REQ-43 The Stop hook fires at the end of every assistant turn, so the gate first classifies the turn, as the prototype does with `classify_message` and `is_finish_attempt` (`reference/armG/register_store.py:716-730`; ported in behaviour, not in code). A message with no question mark is a finish attempt: the gate blocks it while any item is Open, Stale or model-parked, or a branch is under-sized (REQ-35), and allows it otherwise. A message that asks a question is a question turn: it is allowed when the question concerns a logged open item, and blocked when it asks a question that has not been logged. Blocks count against the caps of REQ-42; an allowed finish attempt triggers REQ-23. The exact heuristic and its scenarios are specified in the build plan as conformance scenarios. [assistant]
- REQ-44 The server counts hook calls. A user-sourced answer that arrives when the server has seen no prompt hook is rejected with a message saying hooks are not firing. [user: Q6 option (b)]

## 6. Failure behaviour

- REQ-50 [user] Fail open with visible signals. A register tool failure makes the skill tell the user and continue as a plain interview. The end of the interview states whether the register was complete.
- REQ-51 [user] If the server is absent, grill-me falls back to a plain interview. "Required" becomes "preferred". A notice at the start says no record will be kept, and a notice at the end repeats it. [ADR 0001 Q3]
- REQ-52 After a server crash or restart, the skill offers an explicit resume from the journal or a plain continuation; resume is never automatic. [user] [assistant: mechanics] On start the server looks for an unfinished journal belonging to the project: one whose owning server has exited, which each server shows by holding an advisory lock on its journal file for as long as it runs, so a live concurrent session's journal is never offered for resume. If one exists, `status` reports `resumable` with the interview id and its last event number, and a model-facing mutating call is refused with "unfinished journal: call resume or discard" instead of starting an interview implicitly. `resume` takes an interview id; when exactly one unfinished journal exists the id may be omitted, and when several exist `resume` lists them and requires the id. `discard` archives the journal. Neither is ever implied by another call.
- REQ-53 [open] Whether a failed `mcp_tool` hook shows the user an error is unverified; it is checked in the build and does not block it. Its outcome decides how disruptive a missing binary is in unrelated sessions (REQ-13, REQ-77).

## 7. Journal and decision log

- REQ-60 [user] A write-behind, append-only JSONL journal records every state change and hook event so that `resume` can rebuild state. [assistant: durability] Events are queued and flushed at least at every `check_stop` call and at the end of an interview, so a crash can lose only the events since the last Stop; every event carries a sequence number, and `status` and `resume` report the last one so the loss is visible. [assistant: derived from C3] Every event carries `"v": 2` and `"ts"`; replay accepts events without `v` as v1; an event with `v` above 2 makes resume fail naming the 1-based line number and leaves state unchanged.
- REQ-61 [user] The journal lives in the plugin's per-user data directory (`CLAUDE_PLUGIN_DATA`), keyed by project and interview, with the operating system's temp directory as the fallback if that is unavailable. It is created readable by the user only and is archived, not deleted, when the interview ends (REQ-23); archives older than 30 days are pruned at server start [assistant: the 30 days is a declared constant]. A journal file is named by interview id and is touched only by the server that owns that interview, so two concurrent sessions in one project never share or archive each other's journal. [verified: `CLAUDE_PLUGIN_DATA` is in the server environment, spike 1]
- REQ-62 [user] The decision log is a markdown file written by the server at the end of the interview. It goes in the project's `.scratch/` if that directory exists, otherwise in `decision-logs/` in the project root, which the server creates with a `.gitignore` containing `*` so that the log is not committed by accident [assistant]; it is written readable by the user only. It shows the tree, each answer with source and rationale, parked items and who parked them, reopened and stale history, the implicit-start flag, and hook-health counts. It records the journal's last event position so replay can detect a stale log.
- REQ-63 The grill-me replay step reads the decision log; since the log is rewritten at every allowed finish attempt and the journal is kept while the interview is active (REQ-23), the log's recorded journal position can be compared with `status`; if the log is missing or stale the model falls back to the transcript and says so. [assistant: from ADR 0001 R5]

## 8. Implementations and distribution

- REQ-70 [user] Two implementations are built in parallel as an experiment in working in both languages: Rust and TypeScript on Node (an esbuild single-file bundle). After a while one is kept and the other is retired.
- REQ-71 [user] Both implementations pass the same language-neutral black-box conformance suite (REQ-80), expose identical tool names, schemas and journal format, and have equivalent behaviour.
- REQ-72 [user] The retirement rule is written into the language ADR before the real build starts. Starting values [assistant, for the user to edit]: trigger = both pass the suite and the first five real changes have been applied to both; measures = tokens and failed acceptance runs per change, defects found after merge, release friction; if tokens differ by more than 20% the cheaper one is recommended, within 20% Rust is recommended for its type guarantees; the user decides; the loser is tagged, archived, and removed from CI and releases. Because the second language's agent works from a change already designed once, the language that goes first alternates between changes. Token counts and run counts for each change are recorded when the change is made, in `docs/evidence/language-experiment.md`, never reconstructed from session notifications. Fix-cycle counts are not a measure: the change-request test showed they tie when agents batch changes.
- REQ-73 [user] Distribution is by GitHub releases (the repository is private): per-platform Rust binaries and one `regspike.mjs` for TypeScript. They are installed on the PATH as `regspike-rs` and `regspike-ts`. The plugin starts `regspike-${REGSPIKE_IMPL:-rs}`; if variable expansion in the start command does not work, a small launcher script does the selection. [open: expansion unverified] The names are working names. [assistant]
- REQ-74 [user] The Rust binary is built for Linux x86_64 only for now. The TypeScript bundle needs Node on each machine and is platform-independent. Building locally on a machine remains an acceptable fallback.
- REQ-75 The plugin is installed from a private GitHub marketplace in this repository using the user's existing git credentials (SSH key or credential helper); a prompt-requiring credential helper makes background updates fail silently. A local clone loaded with `--plugin-dir` is the development loop. [verified: docs; private install untested]
- REQ-77 [assistant] The plugin and the binary are versioned separately, so they are checked against each other. `status` reports `server_version` and `tool_schema` (an integer that changes whenever a tool name, parameter or result shape changes); the plugin declares the `tool_schema` it requires, and `begin_interview` and `skill_started` return an error naming both values on a mismatch, which REQ-50 surfaces to the user as "register unavailable: version mismatch". The start command (REQ-73) runs through a small launcher that exits cleanly with that message when the binary is not on the PATH, so a missing binary produces one visible, non-looping failure rather than errors in every unrelated session.
- REQ-76 Install steps and `settings.json` entries (marketplace, enabled plugin, allow rules for the plugin's tools) are filed as dotfiles-repository issues.
