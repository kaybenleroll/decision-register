[user] Second fallback: if a model-facing mutating call (`log_item`, `resolve`, `park`, `reopen`) arrives while no interview is active and no unfinished journal exists (REQ-52), the server starts one, straight into state `active`, and flags it as implicitly started; the flag appears in the decision log. [user] The survival was observed in one trial each, `claude -p` stream-json only; interactive sessions untested, see section 12.   - Rule 1, session id source. The model cannot know its session id. The server records `last_seen_session_id` from every hook call that carries one (`note_prompt`, `check_stop`, `skill_started`), even when no interview is active; `${session_id}` substitutes into UserPromptSubmit and Stop `mcp_tool` hooks and equals the session's id [verified: spike 6, two runs; `skill_started`: spike 4]. An interview started by `begin_interview` or by implicit start binds to `last_seen_session_id`; only if no hook call has been seen does it fall back to the environment variable `CLAUDE_CODE_SESSION_ID` (present at spawn, stale after `/clear`, spike 1). `resume` rebinds to `last_seen_session_id`. REQ-26 compares each later hook call's id with the bound id. [assistant]
  - Rule 2, the invoking prompt counts. While inactive, `note_prompt` sets the `prompt_seen` flag, so the prompt that invoked `/grill-me` counts as prompt 1 at start (REQ-22 reset keeps that one prompt). This lets a decision volunteered in the kickoff prompt be accepted and stops REQ-44 reporting that hooks are not firing. It assumes UserPromptSubmit reaches the server before the start hook for a typed command (unverified, slice V10). [assistant] [open]
  - Rule 3, engagement and stand-down. A hook-started interview is `pending` and becomes `active` on the first successful model-facing register call (`begin_interview` with `mode: register`, `log_item`, `resolve`, `park` or `reopen`; a failing call changes nothing and engages nothing). A pending interview that reaches its second Stop check with no such call is stood down: gate off, log note "skill did not engage". This covers a plain-mode skill, a same-named skill copy without register mode, and a skill whose `status` probe failed. A skill that has detected a schema mismatch or another reason for plain mode calls `end_interview` with `mode: plain`, which stands the interview down at once without flagging it incomplete and records mode plain in the log; if that call itself fails, the engagement rule bounds the harm. [assistant]
  - Rule 4, gate after completion. In `complete` the Stop gate allows every turn; only a deliberate model-facing mutating call returns the interview to `active`. The skill calls `end_interview` after its replay step (slice P5, draft D4). The log of a complete interview is never downgraded (REQ-23). [assistant]
  - Rule 5, exit and resume. Server exit (stdin EOF) on an `active`, not-complete interview writes the decision log flagged "interrupted", keeps the journal as `unfinished` (not archived) and removes the pid file; on a `complete` interview it archives. A journal is `unfinished` iff it has no `end` event and its owner is dead (REQ-52). Unfinished journals older than 30 days are pruned (REQ-61). `resume` claims the journal by creating a fresh pid file exclusively (`O_EXCL`); a second resumer fails with "journal already claimed". A hook start while an unfinished journal exists proceeds; `status` reports `resumable` alongside; mutating calls are refused until `resume` or `discard` (REQ-52). [assistant]

## 4. Data model

- REQ-30 [user] The register is a tree of items. Each item has: id, kind (`question`, `subquestion` or `decision`), text, optional parent, optional `depends_on` ids, status, and event history.
- REQ-31 [user] Status is one of Open, Resolved, Parked, Stale. A Resolved item always carries an answer, an answer source (`user` or `model`) and a one-line rationale; the implementation makes a Resolved item without these unrepresentable where the language allows, and rejects it at the interface where it does not. [assistant: answer and rationale must be non-empty after trimming and the rationale a single line; replay applies the same check and fails resume naming the line, as for REQ-60]
- REQ-32 An answer source of `user` is accepted only if a user prompt arrived since the item's last model action, as counted by the prompt hook; otherwise the call is rejected. [user] `log_item` may carry `answer`, `source` and `rationale` to record a decision the user volunteered in one call; with source `user` it is accepted only if a user prompt arrived since the previous Stop-hook call. [assistant] A user prompt authorises at most one `source: user` answer per distinct item presented since the previous user prompt, with a minimum of 1. [user: gate walk 2026-11-16] Mechanics of that budget: the budget is max(1, p), where p is the number of distinct items the classifier (REQ-43) names as presented since the previous user prompt, so an empty list gives 1; the flat 4 applies only when the classifier returns `unknown` (it errors, times out or cannot parse), which is a distinct result from an empty list [assistant: 4 is a declared constant]. Volunteered `log_item` answers do not draw on this budget; they are limited to 4 per prompt [assistant: 4 is a declared constant]. Residual limit: the budget bounds the damage but does not show that a prompt answered a specific item (section 12, risk 0).
- REQ-33 A Parked item records who parked it (`parked_by`: `user` or `model`) and a reason. A park by the model keeps the item blocking; a park the user asked for does not. [user] `parked_by` `user` is subject to the same user-prompt rule as REQ-32, so the model cannot clear the gate by claiming a user park. [assistant]
- REQ-38 [assistant] Transitions: `resolve` accepts Open, Stale and Parked items (a model-parked item can be resolved, or re-parked with `parked_by` `user` under REQ-33); `park` accepts Open, Stale and model-Parked items; `reopen` accepts Resolved items only; every other transition is an error naming the item id and its current status.
- REQ-34 A `decision` item can be resolved only with source `user`, and parked only with `parked_by` `user`. [user: gate walk 2026-11-16] The rule is derived from the change-request spike's specification C2 and is confirmed as a starting value. [assistant]
- REQ-35 A branch is a parent item with at least N sub-questions; N = 2. [user: gate walk 2026-11-16] N is a declared constant, not measured. [assistant] Enforcement points: `log_item` never rejects on branch size; the finish gate flags a parent that has children but fewer than N. [assistant] The children that count are all children of any kind and any status (the data model has no withdrawn status, REQ-31, so none is excluded). ## 5. Tools and hooks

- REQ-40 Tools: `begin_interview`, `log_item`, `resolve`, `park`, `reopen`, `status`, `resume`, `discard`, `end_interview`, plus the hook-facing tools `note_prompt`, `skill_started` and `check_stop`. Names, schemas and results are identical in every implementation. [assistant: proposal, to be finalised in the build plan] The three hook-facing tools reject any call that carries the model-call marker `_meta` `claudecode/toolUseId`, so the model cannot call `note_prompt` to forge a user prompt or call `check_stop` to spend the caps [verified: spikes 1 and 4 observed that hook-originated calls carry no `_meta` and model calls do, one trial each; a conformance scenario sends both forms]. [assistant]
- REQ-41 Four hook behaviours: the prompt counter (UserPromptSubmit calls `note_prompt`); the finish gate (Stop calls `check_stop` with `last_assistant_message`); and two start hooks (REQ-20). Hooks carry only the fixed input given in their configuration plus substituted fields (for example `${prompt}`, `${session_id}`) [verified: spike 4 for `${prompt}`, `${session_id}` and `${tool_input.skill}`; spike 6 for `${session_id}` in UserPromptSubmit and Stop; spike 1 and spike 4: hook-originated calls carry no `_meta`]. Substitution of `${last_assistant_message}` into the Stop hook's `mcp_tool` input, which REQ-43 depends on, delivered a 6,869-character message with quotes, backslashes, newlines, a question mark, unicode and a JSON fragment byte-identical (length and sha256 matched) [verified: spike 5, one trial, haiku, Claude Code 2.1.325; short and empty messages not tested; `docs/evidence/spike5/`]. Output contract: on UserPromptSubmit, UserPromptExpansion and PreToolUse events the hook-facing tools return empty text or exactly `{}`, never prose; `skill_started` never blocks or denies the Skill call (on a version mismatch it returns `{}` and records the mismatch for `status`, REQ-77); only `check_stop` returns a decision. [assistant] The return text of a UserPromptSubmit `mcp_tool` hook was not visible to the model in two runs [verified: spike 6, haiku, 2.1.325]; whether the return text of UserPromptExpansion and PreToolUse hooks is visible to the model, or can alter the call, is untested (slice V8). [open]
- REQ-42 [user] The finish gate keeps ADR 0001's behaviour as starting values, counted per interview: at most 2 blocks per user prompt, 8 blocks to finish, 12 for unlogged questions; fail open. Claude Code itself limits consecutive Stop blocks to 8, reset by any tool call [recalled: from Claude Code documentation, not re-checked in a repo artefact; verify in the build]; the register's caps sit under that.
- REQ-43 The Stop hook fires at the end of every assistant turn, so the gate first classifies the turn, as the prototype does with `classify_message`, `is_finish_attempt` and `extract_ids` (`reference/armG/register_store.py:679-730`; ported in behaviour, not in code). In states `none`, `pending` and `complete` the gate allows without classifying (REQ-27). A message with no question mark is a finish attempt, except the prototype's exemption for a single labelled one-line request (one non-blank line, fences and URLs removed, that starts with the id label of an open item), which is allowed as a question turn about that item. The gate blocks a finish attempt while any item is Open, Stale or model-parked, or a branch is under-sized (REQ-35), and allows it otherwise. A message that asks a question is a question turn: it is allowed when the question concerns an open item, and blocked when it asks a question that has not been logged. A question concerns an open item if it cites the item's id label (as the prototype's `extract_ids` does) or, failing that, shares at least 3 content words with the item's text. Blocks count against the caps of REQ-42; an allowed finish attempt triggers REQ-23. The classifier also names the items each turn presented, which the per-prompt budget of REQ-32 needs; it returns either a list of item ids (possibly empty) or `unknown` (an error, a timeout or an unparseable message), and the two are distinct results. The exact heuristic and its scenarios are specified in the build plan as conformance scenarios. [assistant] The finish-attempt classifier is confirmed as a starting design; its replay test is REQ-46. [user: gate walk 2026-11-16]
- REQ-44 The server counts hook calls, including those made while no interview is active (REQ-27). A user-sourced answer that arrives when the server has seen no prompt hook call at all (`prompt_seen` never set and no prompt counted) is rejected with a message saying hooks are not firing. [user: Q6 option (b)] The prompt that invoked the skill counts (REQ-27 rule 2), so a decision volunteered in the kickoff prompt is not reported as a hooks failure. [assistant]
- REQ-45 After a compaction the model must be able to recover the tree. `status` returns the full tree: every item with id, text, parent, status, answer and `parked_by`, open items first. Every Stop block's reason names the open items with id and text, for the first 10 items only, each text truncated to 120 characters. A hook that injects the tree after compaction is an upgrade, not a dependency (build-plan slice V7). [user: gate walk 2026-11-16] The constants 10 and 120 are declared constants. [assistant]
- REQ-46 Before the finish-attempt classifier (REQ-43) ships, a replay test runs it over question turns from stored grill-me transcripts and reports how each turn is classified (finish attempt or question turn, and the items named). [user: gate walk 2026-11-16] The corpus is those question turns paired with a hand-labelled register state per turn, for a sample of 30 turns; the labels are made by the assistant and reviewed by the user. The pass criterion is that at least 90% of the sampled turns agree with the labels and that zero finish attempts are classified as question turns [assistant: 30 and 90% are declared constants]. The report is kept in `docs/evidence/classifier-replay.md`. [assistant]

## 6. Failure behaviour

- REQ-50 [user] Fail open with visible signals. A register tool failure makes the skill tell the user and continue as a plain interview. The end of the interview states whether the register was complete.
- REQ-51 [user] If the server is absent, errors, or its `tool_schema` mismatches (the probe of REQ-15), grill-me falls back to a plain interview. "Required" becomes "preferred". A notice at the start says no record will be kept, and a notice at the end repeats it. [ADR 0001 Q3]
- REQ-52 After a server crash, restart or interrupted exit, the skill offers an explicit resume from the journal or a plain continuation; resume is never automatic. [user] A journal is `unfinished` iff it has no `end` event and its owner is dead. Each server shows ownership by writing a pid file holding its process id and process start time beside its journal and removing it on exit; the owner is dead if the pid file is absent, or its recorded process is dead or has a different start time. A journal whose recorded process is alive with the same start time is live and is never offered for resume. (A file lock was rejected because Node has no portable `flock` without a native addon, which would break the single-file bundle.) A hook start while an unfinished journal exists proceeds; `status` reports `resumable` alongside, with the interview id and its last event number; model-facing mutating calls and `begin_interview` are refused with "unfinished journal: call resume or discard" instead of starting an interview implicitly, until `resume` or `discard`. `resume` takes an interview id (when exactly one unfinished journal exists the id may be omitted; when several exist `resume` lists them and requires the id), is accepted only in state `none` or `pending` (a pending interview holds no items and is replaced), rebinds the interview to `last_seen_session_id` (REQ-26), and claims the journal by creating a fresh pid file exclusively (`O_EXCL`); a second resumer fails with "journal already claimed". `discard` archives the journal and is a plain continuation. Neither is ever implied by another call. [assistant]
- REQ-53 [open] Whether a failed `mcp_tool` hook shows the user an error is unverified; it is checked in the build and does not block it. Its outcome decides how disruptive a server that is not connected is in unrelated sessions (REQ-13, REQ-77); a missing binary is covered by the launcher's no-op stub, which makes the hooks succeed silently.

## 7. Journal and decision log

- REQ-60 A write-behind, append-only JSONL journal records every state change and hook event so that `resume` can rebuild state. [user] Events are queued and flushed at least at every `check_stop` call and at the end of an interview, so a crash can lose only the events since the last Stop; every event carries a sequence number, and `status` and `resume` report the last one so the loss is visible. [assistant: durability, derived from C3] Every event carries `"v": 2` and `"ts"`; replay accepts events without `v` as v1; an event with `v` above 2 makes resume fail naming the 1-based line number and leaves state unchanged. [assistant] An `end` event is written when an interview ends; a journal without one whose owner is dead is `unfinished` (REQ-27). [assistant]
- REQ-61 The journal lives in the plugin's per-user data directory (`CLAUDE_PLUGIN_DATA`), keyed by project (the server's `CLAUDE_PROJECT_DIR`) and interview, with the operating system's temp directory as the fallback if that is unavailable. It is created readable by the user only and is archived, not deleted, when the interview ends (REQ-23). [user] An interrupted interview's journal is not archived but stays as unfinished (REQ-27 rule 5); archives and unfinished journals older than 30 days are pruned at server start [assistant: the 30 days is a declared constant]. A journal file is named by interview id and is touched only by the server that owns that interview, so two concurrent sessions in one project never share or archive each other's journal. [verified: `CLAUDE_PLUGIN_DATA` and `CLAUDE_PROJECT_DIR` are in the server environment, spike 1]
- REQ-62 The decision log is a markdown file written by the server. [user] It is written at every allowed finish attempt and at end, interrupted exit and stand-down (matching REQ-23 and REQ-63), never depending on the model. [assistant] It goes in the project's `.scratch/` if that directory exists, otherwise in `decision-logs/` in the project root, which the server creates with a `.gitignore` containing `*` so that the log is not committed by accident; it is written readable by the user only. [assistant] It shows the tree, the skill mode that ran (`register`; `plain` when the skill stood the interview down with `end_interview` and `mode: plain`; or `not engaged` when a pending interview was stood down at its second Stop check; a plain run that never reaches the server has no log), each answer with source and rationale, parked items and who parked them, reopened and stale history, the end kind (normal, "ended incomplete by the model", "ended after completion", abandoned, "interrupted", stood down), the implicit-start flag, and hook-health counts. It records the journal's last event position so replay can detect a stale log.
- REQ-63 The grill-me replay step reads the decision log; since the log is rewritten at every allowed finish attempt and the journal is kept while the interview is active or complete (REQ-23), the log's recorded journal position can be compared with `status`; if the log is missing or stale the model falls back to the transcript and says so. [assistant: from ADR 0001 R5]

## 8. Implementations and distribution

- REQ-70 [user] Two implementations are built in parallel as an experiment in working in both languages: Rust and TypeScript on Node (an esbuild single-file bundle). After a while one is kept and the other is retired.
- REQ-71 [user] Both implementations pass the same language-neutral black-box conformance suite (REQ-80), expose identical tool names, schemas and journal format, and have equivalent behaviour.
- REQ-72 The retirement rule is written into the language ADR before the real build starts. [user] Starting values, confirmed as starting values; the user decides either way: trigger = both pass the suite and the first five real changes have been applied to both; measures = tokens per change, conformance-suite failures on first submission per change, defects found after merge, release friction; if tokens differ by more than 20% the cheaper one is recommended, within 20% Rust is recommended for its type guarantees; the user decides; the loser is tagged, archived, and removed from CI and releases. [user: gate walk 2026-11-16] The five real changes are the first five change requests made after milestone M2 (full suite green in both), not slices I1 to I5. Because the second language's agent works from a change already designed once, the language that goes first alternates between changes: Rust, TypeScript, Rust, TypeScript, Rust. The report also gives mean tokens by role (first versus second implementer), and the 20% margin test uses the paired per-change differences. Defects after merge and release friction are assessed at close-out (slice E1), after the release milestone, not at the fifth change. Token counts and run counts for each change are recorded when the change is made, in `docs/evidence/language-experiment.md`, never reconstructed from session notifications. Fix-cycle counts are not a measure: the change-request test showed they tie when agents batch changes. [assistant]
- REQ-73 Distribution is by GitHub releases (the repository is private): per-platform Rust binaries and one `regspike.mjs` for TypeScript. They are installed on the PATH as `regspike-rs` and `regspike-ts`; the names are working names. [user] `regspike-rs` and `regspike-ts` stay working names, parked until the release milestone (slice R1). [user: gate walk 2026-11-16] The plugin always starts the server through the launcher, which runs `regspike-${REGSPIKE_IMPL:-rs}` and, if the binary is missing, serves a no-op stub instead (REQ-77). [assistant] If variable expansion works in the start command the launcher's selection step can be dropped, but its missing-binary handling stays. [open: expansion unverified, slice V2]
- REQ-74 [user] The Rust binary is built for Linux x86_64 only for now. The TypeScript bundle needs Node on each machine and is platform-independent. Building locally on a machine remains an acceptable fallback.
- REQ-75 The plugin is installed from a private GitHub marketplace in this repository using the user's existing git credentials (SSH key or credential helper); a prompt-requiring credential helper makes background updates fail silently. A local clone loaded with `--plugin-dir` is the development loop. [verified: docs; private install untested]
- REQ-77 [assistant] The plugin and the binary are versioned separately, so they are checked against each other. `status` reports `server_version` and `tool_schema` (an integer that changes whenever a tool name, parameter or result shape changes) and any recorded mismatch; the plugin declares the `tool_schema` it requires. `begin_interview` returns an error naming both values on a mismatch, which REQ-50 surfaces to the user as "register unavailable: version mismatch". `skill_started` never blocks or denies the Skill call: on a mismatch it returns `{}` and records the mismatch for `status` (REQ-41), where the skill's probe (REQ-15) sees it. Whether a failing hook would have been visible is the open check of REQ-53.
- REQ-76 Install steps and `settings.json` entries (marketplace, enabled plugin, allow rules for the plugin's tools) are filed as dotfiles-repository issues.
